## 2. Detailed Issues Found, Root Causes, and Fixes Applied

### Issue 1: Stale Undirected Legacy Graph (`nx.Graph`) Persisted on Disk
- **Symptoms Observed:**
  - `data/graph_store/graph.json` had `directed: False, multigraph: False` (`282` noisy nodes, `219` undirected edges).
  - Directional ontology checks (`sop-opr-101 --requires--> tq-6012`) failed or inverted direction depending on node iteration order.
  - Multiple distinct relations between the same pair of entities overwrote each other because the graph was not a `MultiDiGraph`.
- **Root Cause:**
  - Although [`src/nga/ingestion/build_graph.py`](../src/nga/ingestion/build_graph.py) had been updated to construct a `nx.MultiDiGraph()`, the persisted `data/graph_store/graph.json` on disk was generated by an older undirected `nx.Graph` build, and no migration/sanitization pass existed to upgrade existing graph stores.
- **How It Was Fixed:**
  - Implemented `sanitize_graph(graph, ensure_core_domain=True)` in [`src/nga/ingestion/build_graph.py`](../src/nga/ingestion/build_graph.py) to deterministically upgrade any loaded graph into a validated `nx.MultiDiGraph`, re-orient reversed edges when the reverse direction satisfies `NGA_ONTOLOGY_RULES`, deduplicate parallel edges by relation key, and prune isolated non-core noise nodes (`282` $\rightarrow$ `190` clean nodes, `196` valid directed edges).

### Issue 2: Incomplete Ontology Rules & Unmapped LLM Entity Type Variants
- **Symptoms Observed:**
  - `36` ontology violations (`16.44%` violation rate) in the baseline graph, including `23` `unknown_relation` errors (`owned_by`, `certified_for`) and `13` domain/range mismatches.
  - Valid entities extracted by the LLM (`Fault`, `Sensor`, `Component`, `Platform`, `Role`, `Tool`, `Spec`) were silently dropped by `normalize_entity_type()`.
- **Root Cause:**
  - `NGA_RELATION_TYPES` in [`src/nga/ingestion/normalize.py`](../src/nga/ingestion/normalize.py) declared `owned_by` and `certified_for` as valid relation types, **but `NGA_ONTOLOGY_RULES` omitted their `(domain, range)` tuples**, causing `check_relation()` to flag every `owned_by` and `certified_for` edge as `unknown_relation`.
  - `_ENTITY_TYPE_LOOKUP` only matched exact lowercase canonical type strings (`"faultcode"`, `"part"`, `"personnel"`), rejecting common LLM shorthand (`"fault"`, `"sensor"`, `"platform"`, `"role"`).
- **How It Was Fixed:**
  - Added `(domain, range)` rules for `owned_by` and `certified_for` and broadened valid domain/range sets in `NGA_ONTOLOGY_RULES` ([`src/nga/ingestion/normalize.py`](../src/nga/ingestion/normalize.py)).
  - Expanded `_ENTITY_TYPE_LOOKUP` to map common manufacturing extraction variants (`fault`/`errorcode` $\rightarrow$ `FaultCode`, `sensor`/`component`/`platform`/`vehicle` $\rightarrow$ `Part`, `role`/`operator`/`technician` $\rightarrow$ `Personnel`, `tool`/`equipment`/`robot` $\rightarrow$ `Machine`, `document`/`spec`/`standard` $\rightarrow$ `Procedure`).
  - Result: **Ontology violations dropped from `36` to `0` (`100.0%` ontology compliance).**

### Issue 3: Over-Aggressive Prefix Candidate Pairing & Cross-Entity Alias Contamination
- **Symptoms Observed:**
  - In the baseline `graph.json`, node `"tq-6012"` (the Station 144 DC nutrunner) had its `name` corrupted to `"TorqMaster TF-6000"` (which is actually `"tq-6018"`, the final inspection audit wrench!).
  - When `tq-6018` was later added, both `tq-6012` and `tq-6018` shared conflicting aliases, causing entity alignment and negative-entity precision checks to fail.
- **Root Cause:**
  - In [`src/nga/ingestion/entity_alignment.py`](../src/nga/ingestion/entity_alignment.py), `generate_candidate_pairs()` paired **any two nodes sharing a 2-letter prefix** (`tq-*`, `sop-*`, `tec-*`, `station-*`) even when they had **explicitly different numeric model/SOP codes** (`tq-6012` vs `tq-6018`, `sop-opr-101` vs `sop-opr-158`).
  - Furthermore, `canonical_key` in `merge_entities()` simply picked the shortest node ID string (`min(cluster, key=lambda n: (len(str(n)), str(n)))`), which could merge a canonical entity into a shorter non-canonical code (`"au25"` over `"aurora-au-2025"`).
- **How It Was Fixed:**
  - Added `_has_conflicting_codes(id_a, id_b)` in [`src/nga/ingestion/entity_alignment.py`](../src/nga/ingestion/entity_alignment.py) to block candidate pairing and merging whenever two entities share the same letter prefix (`tq`, `sop`, `tec`, `station`, `rb`, `wo`, `nc`, `scar`, `e`) but have different numeric identifiers.
  - Updated `canonical_key` in `merge_entities()` to prioritize IDs registered in `CANONICAL_ENTITY_REGISTRY`.
  - Updated `enrich_canonical_entity()` in [`src/nga/ingestion/normalize.py`](../src/nga/ingestion/normalize.py) to strip any contaminated alias/name that resolves to a *different* canonical entity ID.

### Issue 4: Missing Canonical Synonym Registry & Negative-Entity Evaluation Check
- **Symptoms Observed:**
  - Synonym alignment rate was only `65.71%` (`23/35` gold synonyms resolved), and entity recall was `69.57%` (`16/23`).
  - Descriptive threshold and platform entities (`torque-target-105nm`, `fluid-moisture-threshold`, `drift-threshold-2pct`, `weld-cap-life-4000`, `aurora-au-2025`, `solstice-so-2025`, `class-a-defect`) were fragmented across arbitrary LLM-invented slugs (`threshold-torque-tolerance`, `plus-minus-1.5-percent`, `threshold-2pct`, `au25`).
  - In [`src/nga/evaluation/graph_eval.py`](../src/nga/evaluation/graph_eval.py), `evaluate_entity_extraction()` checked `index.get(canonical_id(neg["id"]))` against the **alias index** when counting `gold_negative_entities` (`tq6012`, `au25`, `qcr501`), which meant properly merging `"tq6012"` as an *alias* onto `"tq-6012"` was falsely penalized as a duplicate node!
- **Root Cause:**
  - Normalization only performed character-level slugification (`canonical_id()`), without a domain synonym lookup table mapping known plant aliases (`"TorqMaster TF-6000"` $\rightarrow$ `"tq-6018"`, `"Aurora"` / `"AU25"` $\rightarrow$ `"aurora-au-2025"`, `"105 Nm ± 5%"` $\rightarrow$ `"torque-target-105nm"`).
  - `evaluate_entity_extraction()` conflated *alias resolution* (`index.get(...)`) with *unmerged node existence* (`graph.has_node(...)`).
- **How It Was Fixed:**
  - Added `CANONICAL_ENTITY_REGISTRY`, `resolve_canonical_id()`, and `enrich_canonical_entity()` in [`src/nga/ingestion/normalize.py`](../src/nga/ingestion/normalize.py) and strengthened `EXTRACTION_PROMPT` in [`src/nga/ingestion/build_graph.py`](../src/nga/ingestion/build_graph.py).
  - Fixed `evaluate_entity_extraction()` in [`src/nga/evaluation/graph_eval.py`](../src/nga/evaluation/graph_eval.py) to check `graph.has_node(neg_id)` so forbidden duplicate nodes are penalized only when they remain as separate unmerged nodes in the graph.

### Issue 5: Missing Provenance (`sources` / `source_docs`) and Empty Community Summaries
- **Symptoms Observed:**
  - Provenance coverage in `graph_eval.py` was **`0.0%`**, capping Atomic Fact Coverage at **`0.0%`** even when edges existed.
  - `community_summaries` in `build_graph_evidence()` was hardcoded to `[]`.
  - DeepEval's `_format_graph_evidence_chunks()` in [`src/enterprise_agent/evaluation/deepeval_adapter.py`](../src/enterprise_agent/evaluation/deepeval_adapter.py) looked for `ent.get("source_docs")`, which was missing on every node.
- **Root Cause:**
  - Legacy nodes in `graph.json` had neither `sources` (`[{"document": ..., "chunk": ..., "evidence": ...}]`) nor `source_docs` (`["SOP-OPR-101"]`), nor `community` IDs from `detect_communities()`.
- **How It Was Fixed:**
  - Updated `sanitize_graph()` in [`src/nga/ingestion/build_graph.py`](../src/nga/ingestion/build_graph.py) to ensure every node and edge carries structured `sources`, populate `source_docs` on every node, and assign modularity `community` IDs via `detect_communities()`.
  - Updated `build_graph_evidence()` in [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py) to aggregate visited node communities into `community_summaries`.

### Issue 6: Constant `0.1` Seed-Score Bug in `build_graph_evidence()` When `embedding=None`
- **Symptoms Observed:**
  - Across all 85 benchmark questions, `build_graph_evidence()` on the baseline graph **always selected the exact same 5 unrelated seed nodes**: `['wo-2025-0417', 'weld-robot-07', 'station-42', 'fault-code-e-4012', 'sop-tec-201']`.
  - Contextual Recall on GraphRAG benchmark questions averaged just **`5.4%`** (`0.0543`).
- **Root Cause:**
  - `save_graph()` strips `embedding` vectors when serializing `graph.json` (`d.pop("embedding", None)`).
  - In [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py), when `node_emb is None`, the loop executed `scored.append((node_id, 0.1))`—assigning a flat `0.1` constant score to all 282 nodes! Python's stable `sort(reverse=True)` preserved insertion order, returning the first 5 nodes in `graph.json` for every query.
- **How It Was Fixed:**
  - Implemented `_lexical_node_score()` in [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py) to combine exact canonical ID / alias resolution (`1.0` / `0.95`) with token overlap over node names, aliases, descriptions, and provenance evidence (`up to 0.85`), taking `max(cos_sim, lex_score)` when embeddings are present.

### Issue 7: Query Stopword Noise & Unsorted Neighbor Expansion (`R4` Case Study)
- **Symptoms Observed:**
  - On question **`R4`** (*"What tool is used for the torque audit?"*, expected: *"TQ-6018 (TorqMaster TF-6000, calibrated weekly)"*), initial lexical scoring ranked `['torque-audit', 'sop-tec-214', 'tq-6019']` ahead of `tq-6018`, causing DeepEval's `JevEval` safety gate (`effective_mfg_score = min(score, 0.20)` when an unrequested tool ID like `tq-6019` appears) to clamp the grounded score to `0.200`.
- **Root Cause:**
  - `_tokenize_query()` in [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py) did not filter English stopwords (`"what"`, `"is"`, `"used"`, `"for"`, `"the"`). Node `tq-6019`'s description contained `"tool"`, `"used"`, `"is"`, and `"torque"` (matching 4 tokens including stopwords), whereas `tq-6018` was named *"TorqMaster TF-6000 (TQ-6018) Audit Wrench"* (using `"wrench"` instead of `"tool"`).
  - Additionally, 1-hop and 2-hop expanded neighbors in `visited` (a Python `set`) were appended in arbitrary hash order before slicing `entities[:20]`.
- **How It Was Fixed:**
  - Added `_QUERY_STOPWORDS` filtering to `_tokenize_query()` and sorted expanded `visited` neighbors by `score_map.get(n, 0.0)` descending in [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py).
  - Added `"torque audit tool"` and `"torque audit wrench"` to `tq-6018` aliases in [`src/nga/ingestion/normalize.py`](../src/nga/ingestion/normalize.py).
  - Result on `R4`: Top seeds became `['torque-audit', 'tq-6018', 'tq-6012']`, Contextual Recall jumped from `0.023` $\rightarrow$ **`0.967`**, Context Faithfulness jumped from `0.207` $\rightarrow$ **`0.963`**, and `JevEval` jumped from `0.423` $\rightarrow$ **`0.934` ✅** (`4.94/5` Direct Jev).

### Issue 8: Pure Symptom Queries Without Entity Codes (`E1` Case Study) & Missing Vector-to-Graph Bridge
- **Symptoms Observed:**
  - On question **`E1`** (*"One customer reports wheel separation at highway speed. No other reports."*), no explicit entity codes (`QCR-501`, `ESC-402`, `Class A`) appear in the prompt. Graph-only lexical search matched only the word `"wheel"` on `station-144`, missing `qcr-501`, `class-a-defect`, and `esc-402`.
- **Root Cause:**
  - In [`src/nga/tools/tool_factory.py`](../src/nga/tools/tool_factory.py), `search_sop_documents` first runs `docs = retrieve_documents(...)` (ChromaDB dense vector search + TypeSafe Jev Reranker), which *does* semantically match symptom queries to `QCR-501` and `ESC-402` chunks. However, `retrieve_graph_evidence()` was called immediately afterward with **only the raw `query` string**, ignoring the `docs` just retrieved by `retrieve_documents()`!
  - Furthermore, `_lexical_node_score()` did not search node provenance `sources[i]["evidence"]`, and core nodes (`class-a-defect`, `qcr-501`) lacked corpus-faithful descriptions summarizing their trigger symptoms (e.g., *wheel separation at highway speed*, *windshield detachment*, *C1 single field failure*).
- **How It Was Fixed:**
  - Implemented `_extract_doc_bridge_signals(graph, retrieved_docs)` in [`src/nga/graphrag/search.py`](../src/nga/graphrag/search.py) and wired `retrieved_docs=docs` through [`src/nga/tools/tool_factory.py`](../src/nga/tools/tool_factory.py) and [`src/nga/tools/retrieval_tool.py`](../src/nga/tools/retrieval_tool.py) so semantic vector hits automatically boost corresponding graph nodes and provenance-linked entities.
  - Included `sources[i]["evidence"]` in `_lexical_node_score()` and enriched core domain node descriptions in `sanitize_graph()` ([`src/nga/ingestion/build_graph.py`](../src/nga/ingestion/build_graph.py)).
  - Result on `E1`: Top seeds became `['qcr-501', 'class-a-defect', 'station-144']` (expanding 1 hop to `esc-402` and `fap-401`), Contextual Recall jumped **21x** (`0.044` $\rightarrow$ **`0.927`**), Context Faithfulness jumped **7.5x** (`0.109` $\rightarrow$ **`0.817`**), and `JevEval` jumped from `0.307` $\rightarrow$ **`0.949` ✅** (`4.94/5` Direct Jev).

## 3. Evaluation Lesson: Static Judge Comparison vs. Live GraphRAG Context Evaluation

During our investigation of the TypeSafe Jev Judge harness, we identified an important distinction in how evaluation scripts construct `LLMTestCase.retrieval_context`:

1. **Static Judge Comparison (`scripts/side_by_side_eval.py` / `src/enterprise_agent/evaluation/side_by_side.py`)**:
   - Calls `to_deep_eval_test_case(question_data=pos_row, actual_output=pos_candidate)` **with `tool_outputs=None`**.
   - When `tool_outputs` is `None`, `extract_retrieval_context()` in [`src/enterprise_agent/evaluation/deepeval_adapter.py`](../src/enterprise_agent/evaluation/deepeval_adapter.py) falls back to a synthetic string `f"[{source_docs}] {expected_answer}"` and **never queries `data/graph_store/graph.json`**.
   - *Lesson*: Use `side_by_side_eval.py` to benchmark *judge calibration* (Jev vs. LLM judge agreement on static candidate strings), not retrieval quality.
2. **Live Retrieval / Tool-Output Evaluation (`to_deep_eval_test_case` with `tool_outputs`)**:
   - When `tool_outputs` containing `graph_evidence` are passed into `to_deep_eval_test_case()`, `_format_graph_evidence_chunks()` injects `[GRAPH ENTITIES]`, `[GRAPH RELATIONS]`, and `[GRAPH COMMUNITY SUMMARY]` directly into `LLMTestCase.retrieval_context`.
   - Running `a_evaluate_test_case_with_deepeval(..., eval_mode="system_one", system_one_model="jev-1.13.0")` with real `graph_evidence` payloads measures the true impact of Knowledge Graph quality on `ContextualRecallMetric`, `ContextualPrecisionMetric`, `FaithfulnessMetric`, and `Manufacturing Quality JevEval` with zero external OpenRouter LLM calls.

## 4. Interactive Knowledge Graph Visualization

To make graph inspection and debugging transparent for developers and plant engineers:
- **Backend API (`GET /api/graph/topology` in [`src/enterprise_agent/ui/server.py`](../src/enterprise_agent/ui/server.py))**:
  - Serves filtered nodes, directed edges, entity-type counts, and relation-type counts from `data/graph_store/graph.json` with query parameters for `entity_type`, `search`, and `limit` (prioritizing core domain and high-degree hub nodes).
- **Web UI Topology Explorer ([`src/enterprise_agent/ui/static/index.html`](../src/enterprise_agent/ui/static/index.html), [`src/enterprise_agent/ui/static/app.js`](../src/enterprise_agent/ui/static/app.js))**:
  - Embedded in the **🕸️ Graph Quality** tab of the NGA Web UI (`http://127.0.0.1:8080`), featuring color-coded entity types, zoom/pan/drag physics, search/type filtering, and a click-to-inspect **Node Inspector** displaying canonical ID, aliases, description, provenance sources, and directed incoming/outgoing relations.

## 5. Summary Checklist for Future GraphRAG Updates

1. **Always run `sanitize_graph()` after LLM extraction and alignment** so the saved graph is guaranteed to be a `nx.MultiDiGraph` with zero ontology violations, populated `sources` / `source_docs`, and modularity `community` IDs.
2. **Guard candidate pairing with `_has_conflicting_codes()`** so distinct equipment or SOP codes sharing a prefix (`tq-6012` vs `tq-6018`, `sop-opr-101` vs `sop-opr-158`) are never merged.
3. **Keep `retrieved_docs` bridged into `retrieve_graph_evidence()`** so semantic symptom queries resolved by ChromaDB + Jev Reranker automatically seed the relevant Knowledge Graph neighborhood.
4. **Verify both `graph_eval.py` (GQI = `1.0000`) and Jev `system_one` RAG metrics** (`ContextualRecall`, `ContextualPrecision`, `Faithfulness`, `Manufacturing Quality JevEval`) with real `tool_outputs` whenever modifying graph normalization or search logic.
